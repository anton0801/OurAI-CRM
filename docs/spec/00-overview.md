## 1. Core idea: задача, границы и обязательный результат

Ты выступаешь как senior product engineer, frontend engineer, backend engineer и QA engineer. Разработай полноценную внутреннюю CRM для команды, которая производит AI-сериалы, развивает AI-моделей и AI-инфлюенсеров, управляет аккаунтами, контентом и OFM-операциями. Владелец должен видеть работу всей компании, руководители — свои направления, сотрудники — свои задачи и разрешённые проекты. Все разделы используют общие данные.

Система отвечает на вопросы: что производим; для какого проекта и аккаунта; кто отвечает; что нужно сделать дальше; что задерживается; что опубликовано; какие показатели подтверждены; сколько потрачено и заработано по внесённым данным; какие управленческие действия требуются.

### 1.2. Рабочие решения этой спецификации

Название, стек, размеры интерфейса, численные лимиты, стартовая матрица прав, длительности хранения и конкретные политики являются предложенными инженерными настройками. Они определены здесь, чтобы разработчик мог работать без постоянных уточнений. Не выдавай их за отдельно озвученные владельцем требования. Разрешай их изменение через настройки там, где это предусмотрено; изменения архитектуры фиксируй в ADR.

Не разрабатывай iOS-приложение вместо веб-CRM. Не применяй к CRM мобильный шаблон с тремя декоративными onboarding-фонами. Первоначальная настройка здесь состоит из трёх рабочих шагов, которые создают реальные настройки пространства.

Не добавляй встроенную генерацию эротических материалов, отправку сообщений клиентам внешних платформ, банковские переводы, бухгалтерскую отчётность для государственных органов, маркетплейс, публичную регистрацию компаний, платные тарифы CRM или универсальный конструктор приложений. Это не требуется для обозначенного рабочего цикла. Управление контентом и OFM описано как учёт и координация команды.

### 1.3. Критерий полноты

Пользователь может зарегистрировать команду, создать проекты, назначить людей, произвести и согласовать контент, отметить публикацию, внести показатели, провести OFM-смену, зарегистрировать доход и расход, рассчитать вознаграждение, сформировать отчёт и восстановить данные из резервной копии. У всех доступных кнопок есть реализованное действие, сохранение на сервере, проверка прав и состояния ошибок. Демоданные не должны быть обязательны для работы.

## 2. Complete user flow

### F01. Первый запуск владельца
Развёртывание → одноразовое создание Owner через bootstrap-команду → вход → смена временного пароля, если он использовался → настройка MFA → Workspace Setup → создание направлений → приглашение команды → Overview. Bootstrap запрещён после создания первого Owner. В production нет общедоступного admin/admin.

Первый шаг задаёт Name, Timezone, Base Currency. Второй создаёт AI Series, AI Models, AI Influencers с возможностью переименовать. Третий позволяет пригласить сотрудников или пропустить приглашения. Каждый шаг сохраняется на сервере, перезагрузка возвращает на незавершённый шаг. Выбор валюты не создаёт финансовые записи.

### F02. Вход приглашённого сотрудника
Invitation → проверка срока и email → Display Name и Password → подтверждение принятия → MFA при требовании роли → My Work. Приглашение не даёт прав выше указанных отправителем. Повторное принятие открывает вход, а не создаёт второго пользователя. Истёкшее приглашение показывает Request New Invitation; запрос попадает администратору внутри CRM.

### F03. День владельца
Overview → выбор периода и направления → Needs Attention → открытие задержанного проекта → задачи и причины блокировки → назначение ответственного/решение → Review Queue → утверждение материалов → Analytics → исходные записи → Finance → проверка бюджета и выплат. Возвращение в Overview сохраняет фильтры и позицию прокрутки.

### F04. Работа Руслана с сериалом
Projects → New Project, тип Series → концепция и аудитория → Character Profiles → Season → Episodes → сцены и сценарии → шаблон производства → исполнители и сроки → генерация материалов вне CRM → загрузка версий → Review → исправления → утверждение эпизода → размещения трейлеров в привязанных аккаунтах → ручная публикация → регистрация URL → контрольные замеры. Финальный эпизод можно скачать с метаданными; он не отправляется в Dramora автоматически.

### F05. Работа Андрея с моделью
New Project, тип Model → Character Profile → команда → аккаунты Instagram, TikTok и выбранной площадки монетизации → рубрики и недельный план → материалы → согласование → календарь → OFM Assignments → смены → отчёты и доходы → аналитика. Модель остаётся одним Project с доступным OFM-профилем.

### F06. Работа контент-исполнителя
My Work → Task → бриф и reference links → Start Work → при необходимости учёт времени → загрузка версии → обязательный checklist → Submit for Review → уведомление проверяющему. При Changes Requested сотрудник видит замечания к нужной версии, загружает новую, отмечает исправления и отправляет повторно. Согласование старой версии не переносится на новую.

### F07. Работа менеджера публикаций
Calendar → Scheduled Publication → проверка утверждённого файла и подписи → Open Account → публикация вне CRM → Mark Published → URL, Actual Published At → подтверждение → создание задач замера 24h и 7d. Ошибка или отказ публикации оформляется как Failed или Cancelled с причиной. CRM не определяет факт публикации по наступлению даты.

### F08. Полная OFM-смена
My Shifts → назначенная смена → ознакомление с предыдущей передачей → Start Shift → операционные задачи и контакты → регистрация результатов по источникам → Pause/Resume при необходимости → End Shift → отчёт → Submit Report → руководитель Approve либо Request Changes. End Shift фиксирует время, но отчёт может быть завершён позже. При завершении обязательно передать открытые вопросы или явно отметить No Open Items. Зарегистрированные продажи проходят финансовую сверку отдельно от согласования отчёта смены.

### F09. Обновление статистики
Metrics Inbox → список ожидаемых замеров → выбор аккаунта/публикации → Add Metrics → дата фактического наблюдения, период и значения → источник и evidence → предварительная проверка → Save. Для CSV: Upload → Mapping → Validate → Preview → Confirm Import → Result. При конфликте предлагается Skip или Create Revision для конкретной записи; незаметной замены нет.

### F10. Финансовый цикл
Finance → новая операция Draft → поля и подтверждающий документ → Submit → проверка уполномоченным сотрудником → Post → регистрация Settlement при реальном поступлении/оплате → распределение на проекты → Compensation Run → проверка → Approve → запись частичной или полной выплаты. Сверка платформенного вывода связывает поступление с ранее учтённым доходом, не создавая второй доход.

### F11. Повторное использование и завершение
Успешный материал → Duplicate as New Draft → новый бриф, ссылка на источник и выбранные вложения → новые задачи, даты и согласование. Копия не наследует просмотры, публикации, выплаты и статус Approved. Завершённый проект → Archive Preview → разрешение открытых задач, смен и запланированных размещений → Archive. Исторические отчёты продолжают содержать проект.

### F12. Уход сотрудника и восстановление
Team → Member → Deactivate → список незавершённой ответственности → назначение преемников/очереди Unassigned с руководителем → подтверждение → немедленный отзыв сессий → отмена будущих назначений смен → история остаётся с прежним автором. Restore Member не возвращает автоматически прежние чувствительные права. Удалённая в корзину черновая запись может быть восстановлена с проверкой зависимостей и уникальности.
